### Bearer token leaking to external APIs
- **Mistake**: Ktor's `sendWithoutRequest` only skipped auth for paths containing "register" or "openid-connect". Every other request — including pCloud and Google Calendar — received the Keycloak `Authorization: Bearer` header. pCloud returned error 2094 (invalid token); Google Calendar would also reject it.
- **Rule**: `sendWithoutRequest` must check the **host**, not just the path. Only send the bearer token when the request targets our own backend host (`BuildKonfig.BACKEND_URL`). External APIs (pCloud, Google Calendar, any third-party) must never receive our auth header. Pattern:
  ```kotlin
  sendWithoutRequest { request ->
      val backendHost = Url(BuildKonfig.BACKEND_URL).host
      val host = request.url.host
      val path = request.url.encodedPath
      val isBackend = host.isBlank() || host == backendHost
      val isAuthEndpoint = path.contains("register") || path.contains("openid-connect")
      isBackend && !isAuthEndpoint
  }
  ```

### AI identity in Git authorship
- **Mistake**: Git metadata or commit messages may accidentally include Codex/OpenAI/ChatGPT/Claude as author, co-author, co-committer, contributor, or `Co-Authored-By` trailer.
- **Rule**: Never add an AI/tool identity to Git authorship or commit trailers. If an explicit author is required, use Seungjin/SJ's existing Git identity only, and do not change Git config unless explicitly asked.

### BuildKonfig androidMain actual is rewritten by a doLast hook (known debt / footgun)
- **Mistake**: buildkonfig does not support Android product flavors in KMP, so `composeApp/build.gradle.kts` registers a `tasks.whenTaskAdded { if (name == "generateBuildKonfig") doLast { ... } }` hook that **overwrites the generated `androidMain/.../BuildKonfig.kt` with a hardcoded source string** delegating each field to AGP's per-flavor `BuildConfig`. The field list inside that string is hardcoded — nothing keeps it in sync with the real buildkonfig field set.
- **Rule**:
  1. If you add/rename a `buildConfigField` in `buildkonfig { defaultConfigs { ... } }`, you **must** also update the hardcoded `delegatingSource` string in the `whenTaskAdded` block, or the Android actual silently misses the field and fails to compile (or ships a stale value).
  2. The `doLast` action must capture only configuration-time values (`Provider<RegularFile>`, `String`) — **never reference `layout`/`project` inside `doLast`**, or it captures `DefaultProject` and breaks the configuration cache (`cannot serialize object of type 'DefaultProject'`). Resolve paths/content in the `whenTaskAdded` scope and capture those locals.
  3. **Preferred long-term fix** (not yet done): move only the 3 flavor fields (`BACKEND_URL`, `KEYCLOAK_URL`, `KEYCLOAK_REALM`) out of buildkonfig into a hand-written `expect object AppConfig` (androidMain actual reads `BuildConfig`, iosMain actual hardcoded), leave the 4 static `.env` fields in buildkonfig, and delete the `doLast` rewrite entirely. Touches `NetworkClient.kt` + `AuthRepositoryImpl.kt` (4 refs). Verify both Android variants + `iosSimulatorArm64Test`.

### No ktlint in this project — the real format/lint gate is `./gradlew lint`
- **Mistake**: Asked to "run ktlint format", assumed a ktlint/spotless task exists. There is **no ktlint, spotless, or detekt** configured — not in `gradle/libs.versions.toml`, the build files, or as a standalone binary.
- **Rule**:
  1. The actual formatting/lint gate CI enforces (`.github/workflows/pr-check.yml` → `android-common-check`) is **`./gradlew lint`** (Android Lint), plus a TODO grep (`grep -r "TODO" ./composeApp/src` fails the build if any match). When asked to "lint/format" before pushing, run `./gradlew lint` and confirm no `TODO` in `composeApp/src`.
  2. `./gradlew lint` currently reports **3 pre-existing errors** in geofence/notification code from #5 (`MissingPermission` in `GeofenceManager.android.kt` + `NotificationService.android.kt`, `CoarseFineLocation` in `AndroidManifest.xml`) — already on `main`/`develop`. Don't treat these as regressions from your diff; note them in the PR body for reviewers instead of trying to fix them in an unrelated PR.
  3. Product flavors (`dev`/`prod`/`st`) make bare task names ambiguous: use **`testDevDebugUnitTest`** / **`assembleDevDebug`**, not `testDebugUnitTest` / `assembleDebug`. `:composeApp:allTests` additionally fails at the native iOS link step (`linkDebugTestIosSimulatorArm64`, `xcrun` exit 72) when only Command Line Tools are installed — needs full Xcode via `xcode-select`; the shared `commonTest` is still validated on the JVM/Android target.

### buildkonfig targetConfigs match by exact target name — "ios" was dead config
- **Mistake**: `buildkonfig { targetConfigs { create("ios") { ... } } }` was assumed to apply to the iOS targets. It does **not** — buildkonfig matches `targetConfigs` entries by the **exact Kotlin target name**, and the real targets are `iosArm64` and `iosSimulatorArm64`. There is no `"ios"` group. The `create("ios")` block silently never applied, so every iOS build fell through to `defaultConfigs` and shipped `BACKEND_URL=http://10.0.2.2:8080` (an Android-emulator alias, useless on iOS).
- **Rule**: To set per-iOS values in buildkonfig, create a config for **each** target name (`iosArm64`, `iosSimulatorArm64`) — e.g. `listOf("iosArm64","iosSimulatorArm64").forEach { create(it) { ... } }`. After any buildkonfig change, **verify the generated actual**: `./gradlew :composeApp:generateBuildKonfig --rerun-tasks` then inspect `composeApp/build/buildkonfig/iosArm64Main/.../BuildKonfig.kt`. Never trust that a target-config name "looks right".

### Local Codex configuration in repository commits
- **Mistake**: Repo setup included `.codex/config.toml`, which is local Codex application configuration and should not be shared by default.
- **Rule**: Before pushing agent/Codex setup, decide what is shared repo policy versus local developer config. Commit only shared repo assets such as `AGENTS.md`, docs, and reusable project commands/skills. Gitignore local config, caches, personal MCP settings, secrets, and machine-specific files.

- **Mistake**: Replaced/simplified `CLAUDE.md` while setting up Codex instructions, which couples Claude and Codex and prevents both tools from working independently.
- **Rule**: Keep agent instruction files independent. Codex setup belongs in `AGENTS.md` and Codex-specific assets. Do not modify `CLAUDE.md` or other tool-specific instruction files unless explicitly requested.

### `ios-check` CI was red on every PR — Kotlin/Native auto-links private `_LocationEssentials`
- **Mistake**: Spent CI cycles on wrong theories: first added the SDK `PrivateFrameworks` dir to `linkerOpts` (the dir doesn't exist in the simulator SDK), then pinned CI to Xcode 15.4 (failed identically). The `_LocationEssentials` reference is baked into **Kotlin/Native 2.3.0's bundled CoreLocation platform lib**, so it is **independent of the selected Xcode/SDK version**, and the framework is absent from the iOS simulator at **both link and runtime** (a plain stub linked at its real install path then aborts in `dyld` with "Library not loaded").
- **Rule**:
  1. The `ld: framework '_LocationEssentials' not found` failure at `linkDebugTestIosSimulatorArm64` is fixed by a build-time-generated `.tbd` stub under `composeApp/build/ci-frameworks/_LocationEssentials.framework/` (git-ignored via `**/build/`), added to the linker search path with `linkerOpts("-F", …)` on the **`iosSimulatorArm64` target only** — **never** `iosArm64` (device links the real framework). The stub's `install-name` must point at a dylib that exists in the simulator (`/usr/lib/libSystem.B.dylib`) so the runtime load command resolves; no `_LocationEssentials` symbols are actually referenced. See the documented block in `composeApp/build.gradle.kts` (upstream: KT-71566). Remove it once a Kotlin upgrade drops the auto-link.
  2. Before this fix, `ios-check` had been failing on **every** PR (incl. already-merged ones), so PRs were merged on `android-common-check` (lint + TODO grep + `testDevDebugUnitTest`) alone. The iOS gate is now green and enforcing again — treat an `ios-check` failure as a real regression, not background noise.
  3. iOS link/run cannot be validated locally with Command Line Tools only — validate iOS-CI changes via the PR's `ios-check` (≈8 min/cycle), so make each push count.

### iOS TestFlight (Fastlane/gym) signing + the Swift-target compile gap
- **Mistake**: The TestFlight job failed for days with a cascade of errors, each one masking the next because the archive never got far enough to reveal them. Diagnosed in sequence: (a) `No Accounts` / `No provisioning profiles`, (b) App Group entitlement mismatch, (c) a Swift compile error (`missing argument for parameter 'appDeclaration'`). All three were independent.
- **Rule**:
  1. **gym/`build_app` does NOT forward the App Store Connect API key to the `xcodebuild archive` command.** `app_store_connect_api_key` only populates the lane context (used by `upload_to_testflight`). For `-allowProvisioningUpdates` to authenticate during the archive, decode the `.p8` to a file and pass `-authenticationKeyPath/-authenticationKeyID/-authenticationKeyIssuerID` explicitly via `build_app(xcargs: ...)`. Symptom when missing: `error: No Accounts: Add a new account`. (The project's `Config.xcconfig` uses Xcode-16 synchronized-folder syntax — `baseConfigurationReferenceAnchor`/`RelativePath` — which is valid and DOES apply `TEAM_ID`; don't chase the team setting.)
  2. **Automatic provisioning (`-allowProvisioningUpdates`) can toggle capabilities but cannot invent an App Group identifier.** If entitlements request `com.apple.security.application-groups` for a group not registered in the Apple account, the archive fails (`profile doesn't match the entitlements ... application-groups`). For MVP the App Group was unused (no extension/widget targets, no `group.*` code refs) and was removed from both `.entitlements`. It is deferred for a future attendance widget — re-register the group in the portal + re-add the entitlement then. Push (`aps-environment`) is auto-satisfied and kept.
  3. **`ios-check` compiled only the Kotlin side** (`iosSimulatorArm64Test` + `linkReleaseFrameworkIosSimulatorArm64`) — neither touches the Swift `iosApp` target, so Swift↔Kotlin interop breaks only surfaced in the post-merge TestFlight archive (~15 min). Added a PR-time `xcodebuild build -scheme iosApp -sdk iphonesimulator ... CODE_SIGNING_ALLOWED=NO` step (no certs/secrets) to `pr-check.yml`. Keep it — it catches this class of bug before merge.
  4. **Kotlin/Native's Obj-C export drops Kotlin default-parameter values**, so a Kotlin `fun f(x: T = default)` is callable from Swift only as `f(x:)` with an explicit arg. Also, functions whose name starts with `init` are exported with a `do` prefix (`initKoin` → `doInitKoin`, `initKoinIos` → `doInitKoinIos`). Provide an explicit no-arg wrapper for Swift entrypoints (this repo already has `initKoinIos()` in `KoinHelper.kt`).
  5. **Automatic signing is unsustainable for TestFlight on ephemeral CI runners.** With `CODE_SIGN_IDENTITY=Apple Development` + automatic + `-allowProvisioningUpdates`, every run tries to create a new Apple Development cert in the fresh keychain. It archives once, orphaning a cert whose private key dies with the runner; the next run fails with `Revoke certificate: ... private key is not installed` / `No profiles found` (and the 2-cert Development limit). Fix = **fastlane match** (PR #64): a persistent App Store **Distribution** cert + profile in an encrypted git repo, pulled `readonly` into a temp keychain via `setup_ci`, with `update_code_signing_settings(use_automatic_signing: false, code_sign_identity: "Apple Distribution", profile_name: ENV["sigh_<bundleid>_appstore_profile-name"])` before `build_app`. Requires secrets `MATCH_PASSWORD`/`MATCH_GIT_URL`/`MATCH_GIT_BASIC_AUTHORIZATION` and a one-time local `fastlane match appstore` to populate the store. Distribution certs have a separate limit from Development — clean up the orphaned Development certs in the portal too.
  6. **Setting up match on this Mac (the gotchas hit on 2026-06-11):** (a) System Ruby is **2.6.10**, so bundler pins fastlane to **2.230** — and match 2.230's default **V2 (AES-256-GCM) encryption crashes on OpenSSL 3.x** with `couldn't set additional authenticated data`. Run match with **`--force_legacy_encryption true`** (V1 works; CI's newer fastlane still decrypts V1). (b) `bundle install` defaults to the system gem path needing sudo — install locally with `BUNDLE_PATH=vendor/bundle` (git-ignored). (c) match needs **full Xcode**, but `xcode-select` points at CommandLineTools — prefix commands with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`. (d) match stores on the **`master`** branch even though the GitHub repo default is `main` (so `main` looks empty — check `origin/master`). (e) match creates a NEW distribution cert if storage is empty; each failed run orphans one (lost key) — revoke orphans via Spaceship (`Spaceship::ConnectAPI::Token.from_json_file` + `Certificate.all` + `c.delete!`). Identify the live match cert and the two older distribution certs in the Apple Developer portal (Certificates → Distribution); specific IDs are deliberately not recorded here because this repo is public. Verify a cert is unused before revoking it. (f) To run `fastlane match appstore` non-interactively with an API key, build the JSON via `--api_key_path` (`{key_id, issuer_id, key:<.p8 contents>, in_house:false}`).
  7. **App Store Connect requires the iOS 26 SDK (Xcode 26+).** Uploads built with an older SDK are rejected at upload validation: `Validation failed (409) ... This app was built with the iOS 18.2 SDK. All iOS apps must be built with the iOS 26 SDK or later`. Xcode 26 needs macOS 15+, so the iOS CI jobs run on `runs-on: macos-15` and select Xcode via `maxim-lobanov/setup-xcode@v1` `latest-stable` (resolved to 26.3 on the runner). `ios-check` was bumped to the same so the Swift-compile gate matches the archive's SDK.
  8. **Xcode 26 toolchain crashes the Kotlin/Native static-cache builder** on navigation-compose 2.8.0-alpha10's inline `getBackStackEntry`: `e: Failed to build cache ... Function ... getBackStackEntry ... [inline] is not found`. Fix in `gradle.properties`: `kotlin.native.cacheKind.iosSimulatorArm64=none` + `kotlin.native.cacheKind.iosArm64=none`. The cache is a build-time optimization only — binaries are identical, builds just lose the cache speedup. Reproduce/verify locally (this Mac has Xcode 26.0.1): `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer ./gradlew :composeApp:linkReleaseFrameworkIosArm64` (and the SimulatorArm64 debug variant). Revisit (drop the cache-disable) when navigation-compose is upgraded past the alpha or Kotlin fixes the cache builder.

### iOS-only launch crash: `IrLinkageError` from misaligned compose-ecosystem versions
- **Mistake**: The first real iOS run crashed instantly with `kotlin.internal.IrLinkageError: Can not read value from backing field of property 'androidx_lifecycle_viewmodel_compose_LocalViewModelStoreOwner$stable' ... can not be accessed in module <navigation-compose>` (then again in `koin-compose-viewmodel`). Cause: `lifecycle` was pinned to **2.9.6** but `navigation-compose 2.8.0-alpha10` and `koin 4.0.0` were compiled against **lifecycle 2.8.x**; the private `$stable` field ABI changed between 2.8 and 2.9. **Android tolerates this skew; Kotlin/Native's strict IR linkage throws at runtime** (the mismatch shows up only as harmless compile-time "can not be accessed" *notes*). The whole compose stack must be version-aligned for iOS.
- **Rule**:
  1. Keep `lifecycle`, `navigation-compose`, and `koin-compose-viewmodel` on the **same lifecycle line**. For lifecycle 2.9.6 / CMP 1.10.0 / Kotlin 2.3.0: `navigation-compose = 2.9.2` (requires lifecycle 2.9.6), `koin = 4.1.1` (requires lifecycle 2.9.3). Verify a candidate's lifecycle requirement from its `.module` on Maven before bumping. When you bump lifecycle, bump its dependents too.
  2. **Reproduce iOS runtime crashes locally instead of via TestFlight** (this Mac has Xcode 26.0.1). Build + run on the simulator and read the Kotlin stack trace directly — far faster than device logs or CI:
     ```
     export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
     xcodebuild build -project iosApp/iosApp.xcodeproj -scheme iosApp -configuration Debug \
       -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' \
       -derivedDataPath /tmp/dnbuild CODE_SIGNING_ALLOWED=NO
     SIM=$(xcrun simctl list devices available | grep -oE '\([0-9A-F-]{36}\)' | tr -d '()' | head -1)  # or boot an iPhone
     xcrun simctl install "$SIM" /tmp/dnbuild/Build/Products/Debug-iphonesimulator/HanmaumDnApp.app
     xcrun simctl launch --console-pty "$SIM" com.hanmaum.dn.mobile.HanmaumDnApp   # prints the Kotlin crash
     xcrun simctl io "$SIM" screenshot /tmp/x.png                                  # confirm UI rendered
     ```
     Note: the geofence code touches CoreLocation, but it's a lazy Koin `single` not created at launch, so the splash/login path runs on the simulator before any `_LocationEssentials` issue.

### foojay daemon-JVM toolchain broke ALL CI builds (external API 400) — and xcpretty hid it on iOS
- **Mistake**: Both Android (`assembleStDebug`) and iOS (TestFlight archive) CI builds suddenly failed ~5s in, on a commit that built fine locally. Wasted theories first: blamed the marketing-version downgrade (1.1.x → 0.2.0 / "Apple won't allow it"), an Xcode bump, and a poisoned gradle cache — all wrong. The iOS failure surfaced only as `PhaseScriptExecution 'Compile Kotlin Framework' failed, exit 65 / ARCHIVE FAILED` because **fastlane's xcpretty swallowed the real gradle error**. The Android job (no xcpretty) showed the true cause: `Unable to download toolchain (languageVersion=21, vendor=JetBrains) from api.foojay.io ... 400 Bad Request`.
- **Rule**:
  1. Root cause was `gradle/gradle-daemon-jvm.properties` (a Gradle 8.8+ **daemon JVM criteria** file, generated by `./gradlew updateDaemonJvm`) pinning the daemon to `toolchainVendor=JETBRAINS` / `toolchainVersion=21` with **hardcoded `api.foojay.io` redirect URLs**. It worked until foojay started returning 400 for those IDs; fresh CI runners (setup-java = Temurin 17, can't match the JetBrains vendor) must download JBR 21 from foojay and fail at daemon startup — *before any compile*. It passed locally only because JBR 21 was already cached in `~/Library/Java/JavaVirtualMachines`. **Fix: delete the file** so the daemon runs on the installed `setup-java` JDK (17 is fine for Gradle 8.14/AGP 8.13/Kotlin 2.3). Don't re-add `updateDaemonJvm` output — it bakes in foojay URLs and a vendor CI doesn't have. The `foojay-resolver-convention` plugin in `settings.gradle.kts` is inert here (no `jvmToolchain()` in the build) and was left in place.
  2. **When an iOS CI archive fails at the "Compile Kotlin Framework" script phase with a generic `PhaseScriptExecution ... exit 65`, the real gradle error is hidden by xcpretty.** Get it from the matching `android-*` job (plain gradle, unfiltered), or reproduce the gradle task directly — don't trust the xcpretty summary. If a failure hits BOTH platforms on the same commit, suspect shared Gradle/toolchain config, not platform- or Apple-specific causes.
  3. **A marketing-version "downgrade" (e.g. 1.1.1 → 0.2.0) does NOT break the build or get rejected by Apple at archive time.** TestFlight only validates version/build-number at the *upload* step, and accepts a lower `CFBundleShortVersionString` as long as `CFBundleVersion` (here `github.run_number`) stays unique/monotonic. A build-step failure is never an Apple/version issue.

### `gh pr merge --auto` merges IMMEDIATELY when no checks are branch-protection-required
- **Mistake**: Asked to "merge once it's green," ran `gh pr merge 74 --squash --auto`. This repo's `develop` branch protection does **not** mark `android-common-check` / `ios-check` as *required* status checks, so GitHub had no gate to wait on and `--auto` fell back to an **instant merge** while checks were still pending — violating the "once green" condition.
- **Rule**: `--auto` only waits when there is at least one *required* check (or required review) configured in branch protection. When checks are informational (not required), gate the merge yourself: `gh pr checks <n> --watch --fail-fast && gh pr merge <n> --squash --delete-branch`. `gh pr checks --watch` exits non-zero if any check fails, so the `&&` guarantees merge-only-on-green. Don't assume `--auto` enforces a wait.

When the user provides target screenshots for an existing feature area, do not assume they describe a redesign of the current screens. ### Mobile DTO wire names drifted from the backend contract (zip_code, missing houseNumber)
- **Mistake**: `UpdateMyProfileRequest` (mobile) was written without checking the server DTO: it omitted `houseNumber` entirely and used `@SerialName("zip_code")` although the backend is default-Jackson camelCase. Both failed silently — the backend ignores unknown keys and treats missing keys as "keep old value" — so zip edits never saved and users embedded the house number in the street field (then saw it duplicated).
- **Rule**: When writing or changing any request DTO, open the matching DTO in `../hanmaum-dn-server` and copy the exact field names (camelCase, no naming strategy is configured server-side). For PATCH-style endpoints, add a MockEngine test asserting the serialized body's exact keys, and remember null=keep semantics: `encodeDefaults=false` must stay so nulls are omitted.

### `[skip ci]` in a PR body silently skipped ALL workflows on the squash-merge
- **Mistake**: The release-automation PR body had a bullet documenting that version-sync commits carry `[skip ci]`. On squash-merge that body became the commit message, and GitHub scans the **entire** commit message for `[skip ci]`/`[ci skip]` — finding it, it skipped **every** workflow on the develop push (both `distribute.yml` AND the new `release-drafter.yml`), so no ST distribution ran and no release draft was created. Looked like the pipeline "didn't trigger"; the real cause was the merge commit opting out of CI.
- **Rule**: Never let the literal token `[skip ci]` (or `[ci skip]`, `[no ci]`, `[skip actions]`) appear anywhere in a PR title/body that will become a squash-commit message — quote it as `skip-ci` / `\[skip ci\]` / backticked-in-a-way-that-still-contains-it is NOT safe (GitHub matches the substring regardless of backticks). If a push must genuinely be re-triggered after this happens, push a fresh commit to the branch (the config change itself already merged fine as a git operation — only the workflow runs were skipped). Give a workflow a `workflow_dispatch:` trigger so it can be re-run manually without a dummy commit.

### Screen chrome drifted because the spacing scale existed only in prose
- **Mistake**: Every screen built its own header and picked its own padding, so the app read as 20 independent screens that shared a palette. Horizontal padding ran 4/8/10/16/20/24/28/32dp against DESIGN.md §10's mandated 16dp; five different header implementations coexisted (custom Row, title-less `AppTopBar`, raw Material `TopAppBar`, hand-rolled Rows, and no bar at all); three different back glyphs were in use against §9's chevron-only rule. Root cause: `AppColors`/`AppTypography`/`AppShapes`/`AppMotion` all existed as token files, but **there was no `AppSpacing`** — §10's scale lived only in the design doc, so nothing made it enforceable.
- **Rule**:
  1. Every screen renders through `core/presentation/components/AppScreen.kt`. It owns the collapsing large title, the one back glyph (chevron-left, 44dp target), page background, and scrolled-state separation by surface shift. A new screen is consistent by default; opting out needs a comment saying why (`PhotoViewerScreen` opts out because a photo viewer has no title — it still uses the shared back affordance).
  2. **A literal `dp` in a screen file is a review failure.** Spacing comes from `AppSpacing`; if a value isn't in the scale, either it's wrong or the scale needs extending — decide deliberately, don't inline it.
  3. A design rule that exists only in `DESIGN.md` prose will drift. If a rule is meant to hold across screens, it needs a token file or a shared component backing it, otherwise it is a suggestion.
  4. Don't apply window insets in a screen. `App.kt` already wraps the whole `NavHost` in `statusBarsPadding()` and pads it by 80dp when the pill nav shows. Screens that re-applied either got a doubled inset (`AnnouncementDetail`, `MinistryDetail` pushed their overlay controls down by a second status-bar height) or doubled clearance (`ProfileScreen` stacked 160dp of dead space).

### Release Drafter reads its config only from the DEFAULT branch
- **Mistake**: Set up `release-drafter-*.yml` on a feature branch and expected the drafter to work once merged to `develop`. The action failed with *"Configuration file … must reside in your default branch."* Release Drafter's `getConfig` always reads from the repo's **default branch**, regardless of the `commitish` input or which branch triggered the run. The default was the stale `main` (39 commits behind, its `distribute.yml`/lint fixes not yet promoted), so the config was unreachable and `main`'s own `pr-check` was red on pre-existing geofence lint.
- **Rule**: For Release Drafter (and probot-style config actions), the config file must live on the **default branch**. Here the default branch was changed to `develop` (where all CI + activity lives) so the drafter reads config from `develop`; `main` stays the production release branch. When wiring any config-from-default-branch action, confirm `gh repo view --json defaultBranchRef` first and put the config there.
